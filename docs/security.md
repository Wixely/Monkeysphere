# Security and privacy boundary

Monkeysphere stores sensitive personal information. The single administrator, host administrator, volume administrator, backup operator, and trusted reverse-proxy administrator are inside the deployment trust boundary.

The concrete abuse cases, mitigations, accepted risks, and review triggers are maintained in the [initial-release threat model](threat-model.md).

## Initial controls

- No public registration, tenant system, roles, or anonymous record access.
- Domains physically separate records and media for organization within the one-administrator trust boundary. The protected browser selection, explicit remote selectors, per-domain service scope, and separate SQLite/media roots prevent one selected domain from returning another domain's records. Domains are not separate user accounts or protection from the host administrator.
- The unconfigured login is deliberately `admin` / `admin`. Deployment configuration can override the username and can override the password directly or through a password file; Docker Compose exposes interpolated credential settings for deployment overrides. The effective password is hashed in memory with the ASP.NET Core password hasher and is never persisted or logged in plaintext.
- Cookie authentication, explicit sign-out, CSRF validation, bounded session lifetime, and login rate limiting.
- Authentication before record, field, search, remote administration, API, MCP, or detailed diagnostic operations.
- Field merge and conversion are administrator-only application operations. Both require a read-only impact preview and explicit confirmation; a revision fingerprint rejects stale previews, conversion fails closed when any stored value would lose structure or validation, and the final mutation is transactional.
- Record-type retirement and merge use the same administrator-only preview, explicit confirmation, stale-revision rejection, and transactional boundary. Retirement does not erase records, and merging never silently strengthens required-field rules for existing records.
- Authentication before location queries or retrieval. Coordinates, accuracy, and approximation radii are treated as sensitive record data and are returned only through the existing authenticated application and scoped remote-record boundaries. Map queries use an approximation-aware SQLite R-tree, validate geographic bounds, and enforce a maximum 500-row page. The map-pin editor remains provider-free. The multi-record map uses a local graticule by default and requests attributed OpenStreetMap tiles only after an administrator enables them in Settings. The UI warns that the provider receives the IP address, browser metadata, site origin, and enough tile coordinates to infer the viewed area; record names are not placed in tile requests. No geocoding provider is used.
- Authentication before relationship-graph queries or rendering. Search, type filtering, and neighbour expansion execute locally and return at most 500 nodes and 2,000 edges. The vendored Cytoscape.js client makes no external graph-service request, and truncation is disclosed rather than bypassed by the browser.
- Authentication before every image delivery. Uploaded images are byte-, dimension-, pixel-, and format-bounded, decoded before acceptance, stored under opaque paths, and ordinarily rendered through regenerated WebP derivatives with source metadata removed. Retained originals require a separate explicit download action and are returned as non-cacheable attachments.
- Authentication before backup creation, listing, validation, or download. Backup packages are treated as sensitive, returned as private non-cacheable attachments, and contain the domain registry, every domain database, remote-access state, and authoritative original media. They exclude configuration, data-protection keys, administrator credentials, temporary files, and regenerable derivatives; operators remain responsible for storage encryption and access control.
- Restore is offline and requires filesystem/operator access rather than browser access. A data-root instance lock prevents restore through the supported command while Monkeysphere is running; staging validation happens before replacement, and the previous databases and media are retained for operator rollback.
- Contact import can create fields for what a vCard carries beyond the installed ones: categories, address, organisation, job title, structured name parts, social handles, and the Facebook identifier some HTC phones bury in a note. Each is offered with the count of contacts it affects and is created only when an administrator ticks it; creating one adds a field to the Person record type permanently. A note carrying a vendor block is imported without it whether or not anything is enabled, because importing markup nobody wrote is a defect on its own; the block is still retained verbatim as source material. The same fields can be created and filled retroactively from retained source material, which never overwrites a value already present.
- **Fetching a contact photo is the only outbound request Monkeysphere makes, and it is off by default.** A photo carried inside a card is decoded locally and needs no network. A card that only references a photo by web address is not fetched until a person has read the addresses themselves. The import lists every address the server would contact, grouped by host with a count and named against the contact it belongs to, above an explicit warning that contacting a server discloses the deployment's IP address, the time of the import, and the fact that it holds those contacts. Approval is given per host, after the list, and the approval is of specific addresses rather than of the operation: the importer is handed the exact set of approved addresses and refuses any address absent from it, so an address nobody read cannot be contacted even if a fetcher is available. Consenting to a count was deliberately rejected as a design, because the addresses come out of the imported file and a count discloses nothing about who would be contacted. The request is bounded: absolute http or https only, at most three redirects, an image content type, a 10 MiB ceiling enforced while reading rather than trusted from a header, and a 15-second timeout. Only the host is logged, never the address, because a contact photo URL identifies the contact. A photo that cannot be had costs that contact a picture and nothing else, and the existing image pipeline still decodes and bounds whatever arrives.
- Imports retain their raw source material, and it is inspectable. Every line an importer received is kept as it arrived, including custom properties and embedded payloads the application understood nothing about, alongside which import it came from and the content fingerprint of the imported item. This is deliberate: a value that was not mapped exists nowhere else, so discarding it would lose data silently. It is read through the record's own **Imported source data** panel and, over MCP, through `get_record_source` and `read_record_source_value` under the existing `contacts.export` grant, which already returns the same material as a round-tripped vCard. Retained values are summarized with a bounded preview and read in full only through an authenticated, private, no-store, `nosniff` attachment served as `text/plain` whatever the value claims to be, so an embedded payload can never be served as the type it names. Record visibility applies throughout, so a record held back by backstage policy discloses no source material either.
- Backstage is a per-account mode that reveals records held back by backstage policy, and it is unavailable unless the deployment enables `Monkeysphere:Backstage:Available` (`MONKEYSPHERE_BACKSTAGE_AVAILABLE` in the supplied Compose file). A record marked `hidden` is withheld from every ordinary read: search, listings, the relationship graph and its edges, the spatial map, calendar, dashboard, reminders, contact duplicate discovery and contact export all behave as though it does not exist, and the visible records it links to disclose no trace of it. The rule is one predicate applied at every read of records, and an exhaustive leak test enumerates the read surfaces in both directions so that a forgotten path fails the build rather than leaking. Entering backstage lasts 24 hours and then ends on its own; changing a record's backstage state itself requires backstage. Backstage is concealment within one administrator's deployment, not protection from the host, volume or backup administrator: hidden records are stored and backed up like any other.
- Turning the deployment gate off is a kill switch rather than a way to hide the settings section. Existing hidden records stay hidden and become unreachable by everyone, including a remote credential holding the backstage grant, and startup logs a warning naming how many records are affected in which domains and how to reach them again.
- The MCP `backstage` permission lets a remote credential see records held back by backstage policy through the tools it can already use. It authorizes no read on its own, is offered on the MCP surface only, and, unlike the browser's mode, **does not expire after 24 hours**: a credential carrying it sees hidden records on every call until an administrator removes the permission. Existing credentials never gain it automatically.
- DnaX remote access unavailable by default, with separate credentials, randomized routes, bounded requests, and redacted audit metadata when deliberately enabled.
- Minimal unauthenticated liveness response.
- Response headers deny framing and object embedding, restrict cross-site referrers to the site origin, prevent MIME sniffing, and disable camera, microphone, and geolocation browser features. The origin-only referrer is required by the opt-in OpenStreetMap tile service; no cross-site map request occurs while tiles are disabled. A complete script/style CSP remains a documented residual risk while Blazor's generated import map and framework boot resources are assessed for nonce/hash support.

## Transport

The application serves HTTP. External confidentiality depends on an operator-managed HTTPS reverse proxy. Forwarded headers are trusted only from explicitly configured proxies or networks; remote access must not be enabled externally until this boundary is configured and tested.

The built-in credential is public and must be overridden before exposing a deployment outside a trusted local environment.

## Known initial non-goals

There is no application-level encryption of SQLite files, original media, exports, or backups. Host and storage administrators can read them. Original media is retained and can be explicitly downloaded by the authenticated administrator; it may contain metadata that the normalized display derivatives remove. MCP record validation, creation and revision-checked patching, including previewed atomic batches, require the explicit records.write grant. MCP deletion requires a separately selected records.delete grant and an impact preview when dependent data exists. Deletion checks content and dependent-data revisions transactionally and durably queues media removal. Link creation/deletion requires relationships.write; record/relationship-type creation, field creation/attachment, preset installation and onboarding require structure.write. Preset commands require domain-state/catalog revisions; blank selections require acknowledgement and setup inspection is read-only. Field commands check type and field revisions and reject required attachments that leave existing records without values. Link creation checks type and both record revisions; deletion checks the link revision. Mutations, credential-owned retry receipts and redacted audit commit together. Neither new grant authorizes unrelated record writes or data reads. Contact upload, preview, inspection, and transactional import require the separate contacts.import grant. Selected-contact export requires its own contacts.export grant, which authorizes no import and no other record reads. Record image transfer requires media.write to attach and media.read to read back; they are separate because an original returns the bytes as uploaded, which can retain camera metadata such as location that the normalized display copies remove. An upload declares its purpose when it begins, the purpose is persisted with the session, and attaching an upload staged for another purpose fails closed, so contact bytes cannot become an image or the reverse. Other structure changes and runtime administration remain planned. Arbitrary SQL, shell access and filesystem browsing are not provided.


The domains.manage grant includes isolated domain creation and rename as of contract 1.10. Creation takes a new client-generated non-Default UUID, never a server path. Once a reservation is accepted, cancellation or later credential revocation does not undo it; startup can finish it. A new credential cannot replay or take over the old reservation. Existing record-only grants remain unable to manage domains.


Contact upload and validation are exposed under contacts.import in contract 1.12. Session access checks the full credential fingerprint and domain; upload IDs alone do not authorize access. Declared-byte, active-session, retained-metadata and chunk-count bounds constrain staging growth. Expired/cancelled bytes are removed; terminal metadata has bounded retention. Staging is excluded from backup archives and invalidated by successful offline restore. Upload tools authenticate and demand contacts.import before constructing an UploadOwner; the storage owner value is not itself proof of authentication.

Contact preview inspection in contract 1.13 uses contacts.import for both source evidence and matching saved-contact names/IDs/reasons. This authority is part of reviewing duplicate choices and does not require records.read. Adapters authenticate before selecting the domain or resolving handles. Every evidence range checks live credential ownership and source/preview availability. Labels in summaries have explicit truncation flags; complete private evidence is available only through authenticated bounded reads. Inspection audit omits content, names and credentials. Contract 1.14 import apply uses the same grant and checks the captured revision again inside the application transaction. Record/provenance changes, bounded outcome rows, the credential-owned receipt and application audit commit together. Advisory isCurrent never authorizes mutation. Exact receipt replay precedes staging access, while changed payloads and second-key preview reuse fail closed.

Contract 1.15 exposes selected-contact export under a new contacts.export grant. Export is the first tool that deliberately sends record content out of the deployment, so it is separated from contacts.import in both directions: an importing credential cannot export, an exporting credential cannot import, and neither implies records.read. An administrator must select the grant explicitly when rotating a credential; existing credentials never acquire it. The tool accepts only explicit record IDs, so it offers no search, filter or export-everything form and cannot be used to enumerate a domain. Every ID must resolve to an existing Person record in the selected domain, and one unknown, duplicate, foreign-domain or non-Person ID fails the whole request rather than exporting a smaller set. The adapter authenticates and demands the grant before selecting the domain or reading any record. Nothing is staged: the document is regenerated per call from the shared Core export service, so no new transient storage, quota or restore-invalidation surface is introduced. A whole-document SHA-256 digest accompanies every byte range so a client detects records changing mid-read. Export audit records bounded operation metadata only, without record names, IDs or document bytes.
