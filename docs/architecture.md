# Architecture

## Projects

- `Monkeysphere.Core` owns domain types, validation, application commands/queries, and storage ports.
- `Monkeysphere.Data` owns SQLite/Dapper repositories and the application-owned DnaX manifest.
- `Monkeysphere.Web` owns the Blazor host, administrator authentication, UI, HTTP API, MCP tools, and deployment integration.

Core does not depend on Blazor, SQLite, Dapper, or DnaX. Data implements Core ports. Web composes both and is the only network host.

## Data boundaries

The domain registry, domain application databases, and DnaX remote-access database are separate files under one configurable data root. Each owns an independent DnaX manifest and ledger. Remote API and MCP operations call Core query and command services; they do not receive direct database or filesystem access.

Domains are physically isolated spheres within the single-administrator deployment. A stable built-in identifier maps the renameable Default domain to the legacy `monkeysphere.db` and `media/records` paths, so upgrading does not rewrite existing personal data. Each additional domain maps to `domains/{domain-id}/monkeysphere.db` and its own media tree. Every existing repository therefore operates against one selected database instead of depending on repeated row-level predicates; a record identifier from another domain resolves as absent, and cross-domain foreign keys cannot exist.

The browser selection is an authenticated, protected, HTTP-only cookie and a domain switch performs a full navigation so a new Blazor circuit receives a single immutable base selection. The remote HTTP API defaults to the Default domain and accepts an explicit `X-Monkeysphere-Domain` identifier. MCP record tools expose the same choice as an optional `domainId`, scoped to one invocation. Invalid explicit selectors fail closed. The deployment-wide backup format includes and validates the registry, all domain databases, all referenced originals, and remote-access state together.

## Identifiers and values

Migration 21 adds opaque record and record-type revision tokens. SQLite triggers invalidate them for content and validation-schema changes, including direct import/schema-service writes. Record reads use a single snapshot; browser edits submit their original token, and the store compares it again inside the mutation transaction. Media-only changes do not invalidate a content edit. Migration 22 stores bounded per-domain command receipts and committed audit outcomes in the same transaction as record creation/replacement batches. Receipts retain original IDs and revisions for 24-hour retry, followed by seven-day tombstones. Both tables are included in ordinary domain database backup snapshots and cleared by the explicitly enabled debug reset. MCP validate/create/patch adapters use shared Core preparation and this store. Semantic failures have a separate bounded metadata-only audit; migration 23 persists bounded 15-minute record batch previews. Apply uses the same transaction for revisions, all records, receipt, audit and preview consumption. A hosted worker cleans expired previews at startup and every five minutes in explicit per-domain scopes. Migration 24 adds deletion-impact revisions, previews and a durable record-media cleanup queue. Changes to media, links, reminders, graph references and import provenance invalidate deletion review without invalidating ordinary content edits. Database deletion, receipt, audit and cleanup scheduling commit together. Media operations and cleanup coordinate per record; filesystem cleanup retries independently after commit. Other workflow previews and long-operation persistence remain planned.

Domain entities use UUIDv7 identifiers. Each record has one primary display name plus zero or more ordered alternate names in relational child rows. Alternate names are case-insensitively unique within a record, cascade with that record, and participate in bounded text search. Reusable field definitions carry an open string type identifier. Recognized scalar values use typed relational columns; tags use ordered child rows; unknown types use lossless text fallback.

Temporal values retain their explicit precision, a canonical sort key, an approximation flag, and an optional explanatory note. Structured location values use relational child rows containing optional descriptive context, an optional WGS84 coordinate pair rounded to seven decimal places, optional measurement accuracy in metres, and an optional user-declared approximation radius in kilometres. Context-only approximate areas remain valid, while coordinate accuracy requires coordinates. Relationship types use either directional forward/inverse labels or one symmetric label. Relationship rows reference two records relationally; symmetric endpoints are canonicalized to reject reverse-order duplicates.

Coordinate entry is enhanced by a browser-side OpenLayers 10.10.0 editor using only vendored JavaScript and CSS. It renders a local graticule and record pin, converts clicks to WGS84 coordinates, and makes no request to an external tile, geocoding, or mapping service. Typed latitude and longitude remain the authoritative persisted values, so map interaction is optional and the record workflow remains usable without JavaScript map initialization.

The multi-record map is an authenticated read model over structured location rows. Core validates latitude and longitude bounds, record-type and up to 20 selected field layers, page number, and a maximum 500-row page size; the SQLite query supports viewports crossing the antimeridian and returns a deterministic page plus total count. DnaX migration 13 maintains an SQLite R-tree through location-row triggers. Its indexed bounds include declared approximation radii, so an area intersecting a viewport is not lost merely because its centre is outside the viewport. The browser clusters only the returned page, renders declared approximation areas, and exposes linked summaries for selected pins. DnaX migration 18 stores a disabled-by-default external-tile choice. Only after an administrator enables it does the browser add OpenStreetMap's attributed tile layer; otherwise the vendored OpenLayers client renders the provider-free local graticule.

The relationship graph is an authenticated read model over records, aliases, relationship types, relationship rows, record-type symbols, and the identifier of each record's cover image when present. Its default all mode returns every record in the enabled types and uses chosen records only as navigation targets. Connected mode returns chosen records and their immediate neighbours; isolated mode returns only the chosen records. Name-or-alias lookup accepts comma-separated terms and resolves unambiguous matches automatically. Core caps every result at 500 nodes and 2,000 edges and exposes independent truncation flags. The browser receives only that bounded result and uses vendored Cytoscape.js 3.34.0 for pan, zoom, layout, animated centring, selection, directional-arrow rendering, and same-origin authenticated thumbnail backgrounds. Saved coordinates and in-session coordinates anchor existing nodes; newly visible nodes are placed around positioned neighbours with deterministic collision resolution and a minimum centre distance. Drag completion applies the same separation rule. Record-type symbols use a non-interactive HTML overlay synchronized to rendered node positions, keeping them above Cytoscape's separate drag layer. Image bytes continue to flow through the private, no-store media endpoint. Enabled record types are a domain-specific local browser preference. Graph editing remains in record forms; right-click, long-press, and keyboard context-menu gestures expose direct record navigation.

Light and dark presentation share semantic CSS color tokens. A small pre-render browser script restores the explicit `monkeysphere.theme` local-storage preference before CSS loads, while a custom browser event lets canvas-based graph styling update without rebuilding or reloading the graph.

Saved Views is one catalog for typed reusable views with stable UUIDv7 identities. Record views select one record type, ordered field columns, up to ten typed filters, an optional grouping field, and display-name or field sorting. Field references use stable definition identities, so renames do not break views; retired fields remain visible until the administrator edits the view. Graph views use a separate relational schema suited to their display mode, ordered selected-record identities, ordered enabled-type identities, and bounded per-record coordinates. Position rows cascade with either the saved view or record. Keeping the schemas separate prevents graph concepts from weakening record-grid validation while giving both kinds one discovery surface. View rows are rendered through authenticated Core queries rather than direct browser or filesystem access.

The authenticated calendar is a read model over record field values and introduces no duplicate event storage. Exact-date values and non-approximate temporal values with day precision are eligible for day placement; approximate values and century, decade, year, or month precision are excluded because they cannot honestly identify one day. Calendar queries are bounded to 367 days and 1,000 entries, accept optional record-type and field-definition filters, and return stable record links for both the month grid and upcoming-date list.

The authenticated dashboard is a separate projection over records and administrator-selected recurring fields. DnaX migration 15 introduced the bounded look-ahead period and date-field identities; migration 17 adds an ordered set of front-page record categories while migrating the former single selection without loss. With no saved configuration, the installed People preset and its canonical Birthday field are selected automatically. Exact dates and non-approximate temporal values with day, minute, or second precision recur annually; the projection preserves times where available, calculates the next local occurrence without changing the source value, and clamps 29 February to the final day of February in non-leap years. Approximate and coarser values remain excluded. Each category reads a bounded page through the ordinary Core search service. Rows use the authenticated thumbnail endpoint for a cover or first image and otherwise render the record-type symbol as a local placeholder.

In-app reminders use DnaX migration 10 and identify a logical record field value by record, field definition, and ordinal. This preserves an active reminder when the date or unrelated record details change, removes it when the eligible value is removed, and lets field merge/conversion workflows carry the reminder forward. Reminders remain behind administrator authentication and have no external notification transport. Manual iCalendar export applies the same bounded eligibility query, emits all-day RFC 5545-style events with stable local UIDs and folded UTF-8 content lines, and is returned as a private, non-cacheable attachment rather than a hosted feed.

vCard interoperability is an authenticated, one-time transfer workflow for the installed Person preset. A bounded UTF-8 parser accepts versions 3.0 and 4.0, unfolds and validates content lines, preserves property groups, parameters, raw values, and extensions, and fingerprints each card. Preview maps the first compatible email, phone, birthday, URL, and note to canonical preset fields; additional or incompatible values remain opaque. Duplicate evidence combines exact prior-import fingerprints with names, aliases, normalized email and phone values, and comparisons with earlier contacts in the same uploaded file. Exact cards and a single strong in-file email or phone match default to skip; name-only matches remain visible for review without being silently collapsed. The administrator chooses create separately, skip, merge non-conflicting values, or replace mapped values for every contact before one SQLite transaction begins.

DnaX migration 11 stores import fingerprints and semantic property provenance. Mapped provenance follows field merge/conversion; opaque properties, including grouped Apple labels, survive export even when the local field model cannot display them. vCard 4.0 export regenerates current names and mapped values, reuses applicable source parameters/groups, includes preserved opaque properties, folds UTF-8 lines, and is limited to 100 explicitly selected Person records per download. Imported source credentials and files are never retained.

Field-schema evolution is an authenticated Core workflow over the existing relational identities. A compatible merge requires identical type identifiers and configurations, previews attachments, values, record conflicts, and saved-view references, and applies an explicit conflict policy in one SQLite transaction. Duplicate attachments preserve the stricter required setting; duplicate saved-view columns collapse onto the retained definition. The source definition remains as a retired history row. Preview results include a deterministic revision fingerprint over affected definitions and references; the mutation transaction recalculates it and rejects stale confirmation.

A conversion previews every source value against a proposed new local definition. Scalar conversions reuse the ordinary target validator; exact dates can become day-precision temporal values and only exact, non-approximate day temporal values can become exact dates. Tags, locations, and richer temporal values are not flattened. Application is all-or-nothing: create the new definition, replace validated values, move type and saved-view references, and retire the source in one transaction. These operations change data but not the database schema, so they require no new DnaX schema migration.

## Record images

Images are a record-level capability rather than configurable preset fields. SQLite stores ordered metadata and cascades it with the owning record. DnaX migration 12 adds bounded captions, one cover per record, stable manual order, and non-destructive rotation/crop settings. Validated originals and generated display derivatives live under opaque UUID-based paths within `media/records` beneath the configured writable data root. The application decodes JPEG, PNG, and WebP uploads with bounded byte, dimension, and pixel limits, then creates metadata-stripped WebP previews and thumbnails with SkiaSharp. Corrections regenerate only those derivatives from the retained original. Display and explicit original-download endpoints require authentication, use private no-store caching and disable MIME sniffing; original filenames become attachment metadata but never determine filesystem paths.

## Backups

Backup creation is application-owned, following DnaX's documented boundary: DnaX supplies the authoritative manifests and migration lifecycle while Monkeysphere chooses and tests its SQLite backup strategy. Format 2 is explicitly deployment-wide. The service snapshots the domain registry first, uses that snapshot as the authoritative domain set, then uses SQLite's online backup API for every listed domain database and remote-access state before packaging only database-referenced original media from each domain. A versioned JSON manifest records the domain catalogue, SHA-256 checksums, byte lengths, entry kinds, application version, and application schema version. Validation rejects unsafe or duplicate archive paths, an inconsistent registry/domain list, unmanifested entries, mismatched checksums, incompatible future schemas, SQLite integrity or foreign-key failures, and missing or surplus original media before a package is exposed for download. Format 1 single-domain packages remain valid and restorable.

Restore runs as an offline executable mode before dependency injection, database migration, or HTTP startup. A data-root lock excludes a running Monkeysphere instance. Restore extracts into a same-root staging directory, repeats path, checksum, SQLite, DnaX-ledger-version, registry/domain, and media-reference validation, then swaps the registry, all domain databases, remote-access state, and authoritative media while retaining the former live set as a rollback directory. Configuration, keys, backup history, and other operator-owned files are untouched. Missing display derivatives are rebuilt lazily from the restored originals and persisted correction metadata.

An optional hosted scheduler uses the same verified creation operation. Daily, weekly, and monthly schedules resolve their configured local execution time through an explicit time-zone identifier; invalid daylight-saving times advance to the first valid minute. Retention is bounded from 1 to 1,000 packages and is applied only after successful creation, preserving the newest packages first. Scheduling defaults to off and is deployment-configured, including through Docker Compose variables.

## Presets and first-run setup

The project-owned catalogue defines concrete, versioned record-type presets in Core. Installed record types and fields receive fresh local UUIDv7 identities while retaining preset provenance and canonical field keys. They use the same editable tables and services as administrator-created definitions; presets are not hard-coded subclasses.

Starter packs are curated selections over that catalogue. A new authenticated dataset can select one of four complexity levels, preview example items, and remove unwanted presets before confirming. The Data implementation installs all selected types, fields, applicable relationship types, and setup completion in one SQLite transaction. The explicit blank-slate choice writes completion without creating types. Migration 5 marks datasets that already contain record types as initialized so upgrades do not enter onboarding.

Record types have active or retired lifecycle state through DnaX migration 9. Retirement keeps records, fields, views, preset provenance, and stable identity intact while blocking new records and attachments. A type merge previews record, view, field, and requiredness effects with a revision fingerprint, then moves records and views to an active target transactionally. Shared attachments remain required only when both schemas required them; source-only fields append as optional; target-only requirements relax when moved source records could not satisfy them. The retained target keeps its identity and provenance, and the source remains as retired history with its original field attachments.

The Home, Workplace, Favourite Place, and Event catalogue entries are version 2 after replacing their version 1 descriptive-location and separate-radius fields with one structured location field. Fresh installations receive version 2. Existing locally owned version 1 definitions remain unchanged until an explicit preset-upgrade workflow is implemented.

## Relationship concurrency

Migration 25 maintains opaque relationship-type and link revisions with database triggers, including changes made by existing preset or storage paths. A type change also invalidates its links. Shared browser handlers carry the revisions they displayed into type rename/retirement, link creation and removal. Rename, retirement and deletion compare revisions within their SQL statements; creation holds an immediate transaction across active-type/revision validation, insertion and readback. Type creation reads its generated revision before committing. MCP relationship reads expose these tokens. Scoped relationship commands reuse the same Core normalization and transactional Data helpers. Their mutations, credential-owned receipts and redacted audit share one transaction and the existing bounded command history. Link creation additionally checks both record revisions.

## Schema creation commands

Migration 26 gives reusable fields persistent revisions that change with metadata, configuration, lifecycle and provenance. Field discovery includes these tokens. Browser and MCP field-addition paths validate captured revisions and reject required attachments when existing records lack values. Shared Data helpers perform record-type creation, field creation and attachment within caller-owned transactions; MCP mutations, receipts and audit commit together. Field creation receipts include both the new field and the changed record type, while attachment receipts identify the changed type. Unknown field type identifiers retain the Core text fallback.

## Onboarding command state

MCP setup inspection reads setup, record-type metadata/revisions and relationship-type revisions in one read transaction. A domain-bound hash describes that snapshot; a separate packaged-catalog hash covers definitions and selection rules. Inspection reports implicit completion for existing types without persisting it or inventing a completion timestamp. Preset commands validate both revisions, then reuse the browser installer inside the command receipt/audit transaction. Interrupted domain creation needs a registry-owned reservation and publication workflow before it can be exposed safely; this is still planned.

Domain registry migration 2 tracks opaque name revisions independently of the per-domain application schemas. Browser rename checks the displayed revision in the update transaction. The same transaction reads a prospective immutable catalog; cancellation is checked before commit, then commit and cache publication finish together without a caller cancellation interrupting publication. Failed validation or cancelled pre-commit work leaves the old snapshot intact. MCP domain reads expose the tokens for future registry-backed commands.


Registry command persistence (2026-09-07): domain rename shares browser revision validation and serializes through the catalog gate. Registry migration 3 stores rename receipts and redacted command audit in the same transaction as the name update; the cached snapshot is published only after commit. Replay returns the stored outcome without republishing historical domain state. Deployment-wide snapshots include these registry tables.


Registry migration 4 (2026-09-07) adds DomainCreations. Before initializing any non-Default database, browser/MCP creation reserves its ID and name. Ready domains remain in Domains; pending entries cannot resolve through catalog scopes. Initialization is idempotent; startup resumes all reservations before serving requests. Final registry insertion, MCP receipt/audit and reservation deletion commit together, followed by cache publication. No request-failure path deletes the owned directory. Browser retries can resume a pending browser name; MCP retries require the original credential/action/key/target/hash. Registry-first backups capture either pending intent (recreated on restore) or a published domain (database included). A recovery fault prevents startup until corrected.


Structured search (2026-09-07): query_records reuses the application search rules and SQLite predicates. Its adapter enforces records.read, strict bounds and domain-local type/filter/sort references; legacy search_records retains its compatibility behavior. The shared store uses one deferred read transaction for count and paged results. Exact-date comparisons normalize to midnight before comparison with temporal sort keys; numeric comparison bounds must be finite. New query errors carry bounded structured metadata without database exception details.


Contact staging foundation (2026-09-07): remote-transfers.db has its own project-owned DnaX manifest and contains session metadata plus bounded binary chunk rows. It is deployment-wide so quota reservations serialize in one database transaction, while every session lookup checks domain and credential fingerprint. Chunk insertion and offset advancement commit together; hash verification and copying read one bounded chunk at a time. Startup migrates staging and removes expired bytes; a separate worker repeats cleanup every five minutes. Backups omit staging. Successful offline restore invalidates old staging and removes its files from the rollback copy. Internal sealing verifies integrity only; contact semantics, audit and remote adapters remain unfinished.


Streaming vCard validation (2026-09-07): a scoped upload read lease pages through immutable sealed chunk rows inside a read transaction. Core ContactUploadService uses VCardParser.ParseAsync to validate this stream after integrity sealing. The parser shares its unfolding/property/card state machine with the synchronous browser parser, reads bounded UTF-8 buffers and preserves extension properties and canonical fingerprints. The lease cannot be retained for use after the callback; a callback that returns without reading all bytes is rejected. Upload state is rechecked after the snapshot is released. This operation parses contacts without mutating domain records; remote audit, adapters and durable import previews are still pending.


MCP upload adapters (2026-09-07): five lifecycle tools use contacts.import and the shared authenticated credential-fingerprint provider. Their effective decoded limits derive from the configured request ceiling; no URL/file-path integration is introduced. Internal integrity sealing is separate from streamed content validation, and completion returns only status/count. Staging schema 2 stores redacted upload audit. Begin, chunk, seal and cancellation write their audit in the same transaction; content-validation success and bounded failure codes are recorded separately. Expired audit is swept with staging cleanup, retaining at most 50000 rows/seven days. Contact import still requires durable preview/apply.

Contact export (2026-09-07): `export_contacts` reuses the same bounded Core `IVCardService.ExportAsync` path as the authenticated browser download, so the remote and browser documents cannot diverge. It is stateless by design: the document is regenerated from current records on every call rather than staged, which keeps the upload path's quotas, expiry sweeps and restore invalidation out of a read-only operation, at the cost of repeating the bounded 1-100 record read per byte range. A whole-document SHA-256 digest returned with every range lets a client detect records changing between ranges and restart. Ranges follow the same offset/nextOffset contract as import evidence, including an empty final range at the end offset. A separate contacts.export grant keeps outbound contact data distinct from contacts.import in both directions.

Contact preview concurrency (2026-09-07): application migration 27 maintains a persistent domain import revision. Record, structure and provenance changes invalidate previews; existing child-data revision triggers cover aliases and field values. This conservative domain-wide guard can also invalidate a preview after unrelated record changes. Preview checks the revision before and after discovery, and apply checks it inside the write transaction. Rollback restores the revision. Browser preview uses streaming parsing and clears stale previews for reselection. Import preparation and transactional application are shared entry points for future durable MCP imports. Empty canonical-value query results are supported during duplicate discovery.
Durable contact previews (2026-09-07): staging schema 3 separates headers from ordered contact JSON payloads so inspection can page through complete evidence. Shared Core preview generation runs against the selected domain and captured import revision. Creation and redacted upload audit share the staging transaction; duplicate retry keys serialize to one stored result. Source-upload cancellation removes dependent payloads atomically. Expired payloads and identifying header text are cleaned by the shared staging sweep; metadata tombstones prevent accidental retry-key reuse. The later import apply must put its receipt/outcomes in the application database transaction and replay that receipt before consulting expiring staging. No cross-database mutation atomicity is claimed by preview storage.

Contact import commands (2026-09-07): application migration 28 stores a compact receipt separately from ordered per-contact outcomes. The service hashes ordered selections and checks a matching receipt before staging, allowing exact retries after preview/upload loss. On a first attempt, a staging transaction leases the immutable preview while Core prepares it. The application write transaction rechecks the domain import revision, applies all records/provenance, captures final record revisions, and commits receipt, outcomes, and audit together. A unique preview ID prevents a second apply key from consuming the same review. Staging is temporary; committed results are part of each domain database and normal backups.
