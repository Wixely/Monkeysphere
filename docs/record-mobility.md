# Record mobility and hidden domains

Status: Hidden domains implemented (registry migration 6). Linking and moving designed, not built.
Supersedes the "previewed record transfer/copy" line in
[roadmap](roadmap.md) and requires the TM-16 review that line calls for.

Three related capabilities:

1. **Move** a record from one domain to another.
2. **Link** a record so that it exists in two domains at once — deliberately rare.
3. **Hide** a domain, so that it is observable only from backstage.

## What "exists in both domains" can and cannot mean

A domain is a separate SQLite database and a separate media root. Every repository resolves its
connection from `ICurrentDomain.Id`, so every query in the application runs against exactly one
domain's file and no query spans two. Record type identifiers are minted freshly per domain at
preset install, so even Person is a different identifier in each domain.

One row being simultaneously in two domains is therefore not expressible without collapsing every
domain into one database and adding a domain predicate to every query — which is precisely the
design domains exist to avoid, and which would dissolve the isolation invariant that TM-16 and
the whole domain test suite rest on.

**A linked record is therefore two real rows that the application knows are the same object.**
Each domain holds an ordinary, local, independently queryable record. A shared link identity
joins them, one side is authoritative, and changes propagate. Every existing query, backstage
predicate, media path, relationship, and isolation test continues to hold unmodified, because
from any single domain's perspective nothing has changed.

## Invariants

- Linking never introduces a cross-domain foreign key, a cross-domain join, or a read that opens
  two domain databases in one query. The isolation invariant is preserved exactly.
- Every linked record is a complete, self-sufficient record in its own domain. Deleting the other
  domain, or restoring a backup that predates the link, leaves a valid record behind.
- One side is **home** and is the only writer. Twins are read-only where they are linked.
- Propagation is durable and eventually consistent. It is never claimed to be atomic.
- A link is only possible between records whose type resolves on both sides by preset key.
- Backstage state propagates along a link. A hidden record's twin is hidden.
- Moving is linking plus removing the source, and uses the same machinery and the same preview.

## Link identity

Per-domain, in each domain database (migration 33):

```sql
CREATE TABLE RecordLinks (
    RecordId TEXT NOT NULL PRIMARY KEY,
    LinkId TEXT NOT NULL,
    HomeDomainId TEXT NOT NULL,
    IsHome INTEGER NOT NULL CHECK (IsHome IN (0, 1)),
    SyncedRevision TEXT NOT NULL DEFAULT '',
    SyncedAtUtc TEXT NOT NULL DEFAULT '',
    State TEXT NOT NULL DEFAULT 'linked'
        CHECK (State IN ('linked', 'diverged', 'broken')),
    FOREIGN KEY (RecordId) REFERENCES Records(Id) ON DELETE CASCADE
);
CREATE INDEX IX_RecordLinks_LinkId ON RecordLinks(LinkId);
```

Deployment-wide, in the domain registry, so that "which domains hold link L?" is answerable
without opening every domain database in turn:

```sql
CREATE TABLE RecordLinkIndex (
    LinkId TEXT NOT NULL,
    DomainId TEXT NOT NULL,
    RecordId TEXT NOT NULL,
    IsHome INTEGER NOT NULL CHECK (IsHome IN (0, 1)),
    PRIMARY KEY (LinkId, DomainId)
);
CREATE UNIQUE INDEX UX_RecordLinkIndex_Home ON RecordLinkIndex(LinkId) WHERE IsHome = 1;
```

The registry index is a convenience projection, not the truth. Each domain's own `RecordLinks`
row is authoritative for that side, so a registry that is lost or restored stale can be rebuilt
by reading each domain once, and a link never depends on the registry to remain valid.

## Keeping twins in sync

### Detecting change costs nothing

`Records.Revision` is already regenerated by trigger on every content change — display name, type,
aliases, field values, field-value tags and locations — and universal tags join that set. Asking
whether a record has changed since it was last propagated is therefore a string comparison
against `SyncedRevision`, with no new change tracking and no polling of content.

### Propagation is a durable queue, because it cannot be a transaction

Two domains are two SQLite files. There is no distributed transaction, so a change cannot be
committed to both in one atomic step. Writing through to both databases inside one operation can
crash half-applied, leaving two rows that disagree and nothing that records the fact.

Propagation is therefore staged the way durable media cleanup already is: the edit commits to the
home domain alone, and in the same transaction a work item is enqueued. A worker drains the queue,
retrying at startup and on a timer, and a failed or deferred propagation leaves the twin merely
stale rather than corrupt.

```sql
CREATE TABLE RecordLinkOutbox (
    LinkId TEXT NOT NULL,
    TargetDomainId TEXT NOT NULL,
    SourceRevision TEXT NOT NULL,
    Operation TEXT NOT NULL CHECK (Operation IN ('upsert', 'unlink', 'backstage')),
    EnqueuedAtUtc TEXT NOT NULL,
    LastAttemptAtUtc TEXT NOT NULL DEFAULT '',
    PRIMARY KEY (LinkId, TargetDomainId)
);
```

The primary key collapses repeated edits: ten edits to a record before the worker runs leave one
pending item carrying the newest revision. Propagation copies current state rather than replaying
a change log, so a coalesced item loses nothing.

### Fields are matched by canonical key, never by identifier

The home domain's `birthday` field identifier means nothing in the target domain. What is stable
across domains is `RecordTypes.PresetKey` and `FieldDefinitions.CanonicalKey`, both already
present and both already uniquely indexed.

Propagation therefore:

- resolves the target record type by preset key, and refuses the link if the target domain has
  not installed it;
- maps each source field value to the target field with the same canonical key;
- copies aliases, images, universal tags, and backstage state, none of which need mapping;
- and reports every source field that has **no** canonical key — an administrator's own custom
  field — as unsynced, in the preview, before the link is made.

Silently dropping a custom field would make the twin quietly lossy. Naming it up front lets the
administrator give the target domain a matching field, or accept the omission deliberately.

Relationships are deliberately **not** propagated. A relationship names two records in one domain,
and its counterpart may simply not exist in the target. Twins are linked records, not linked
subgraphs.

### Convergence and conflict

Before applying, the worker compares the twin's current `Records.Revision` with the
`SyncedRevision` stored on its `RecordLinks` row:

- **equal** — the twin has not been touched since it last absorbed a propagation, so the update
  applies cleanly and `SyncedRevision` advances to the source revision just applied.
- **different** — something edited the twin directly. The twin is not overwritten. The link moves
  to `diverged` and surfaces for the administrator to resolve by re-pushing from home or breaking
  the link.

Because twins are read-only where they are linked, `diverged` should only arise from a restored
backup or a direct database edit. Treating it as a first-class state rather than an impossibility
is what keeps a restore from silently discarding data.

### Single writer

The home domain is the only writer. This is the one model that converges without a conflict
resolution interface, and multi-writer merge semantics would have to be defined separately for
each of the ten field types. Editing a twin where it is linked is refused with an action that
opens the record in its home domain. Home can be reassigned explicitly.

## Deletion

Deleting a home record does not delete its twins. It breaks the link, leaving each twin an
ordinary independent record, and enqueues an `unlink`. Cross-domain cascade would mean a deletion
preview that reaches into other domains to count dependent data, which widens the deletion
impact surface well beyond what `records.delete` currently describes.

Deleting a twin removes only that twin and unlinks it.

## Backstage and linking

A twin must never be a way around backstage. If a record is hidden in its home domain, a twin that
appeared as an ordinary record elsewhere would disclose exactly what TM-17's exhaustive leak test
exists to prevent.

- Backstage state propagates along the link and is part of every `upsert`.
- Creating a link from a hidden record requires backstage, as changing a record's state already
  does.
- Hiding a record enqueues a `backstage` propagation to every twin, and that propagation is
  applied ahead of ordinary content updates.
- The leak test gains linked records: a hidden record with a twin must reach no ordinary read
  surface **in either domain**.

## Hidden domains

A domain may be marked hidden. A hidden domain is observable only by a caller who holds backstage,
reusing the existing availability gate, per-account time-boxed activation, and grant.

```sql
ALTER TABLE Domains ADD COLUMN IsHidden INTEGER NOT NULL DEFAULT 0
    CHECK (IsHidden IN (0, 1));
```

- The Default domain cannot be hidden. It is the fallback that invalid selections resolve to, and
  a hidden fallback would leave an ordinary caller with no domain at all.
- `IDomainCatalog.Snapshot` is filtered by backstage visibility, so the header switcher, domain
  settings, and every enumeration omit hidden domains without each having to remember to.
- Selecting a hidden domain without backstage fails closed, exactly as an unknown domain does —
  the two are deliberately indistinguishable, so selection cannot probe for hidden domains.
- A protected cookie that selects a now-hidden domain resolves back to Default rather than
  erroring, matching how obsolete selections already behave.
- Remote surfaces treat a hidden domain as absent unless the credential carries the backstage
  grant. Domain listing, `X-Monkeysphere-Domain`, and MCP `domainId` all apply the same rule.
- Leaving backstage while a hidden domain is selected returns the session to Default.
- With the deployment backstage gate off, hidden domains are unreachable by everyone, including a
  credential holding the grant, consistent with the gate being a kill switch. Startup warns with
  the count, as it already does for hidden records.
- Backups remain deployment-wide and include hidden domains. Backstage is concealment within one
  administrator's deployment, not encryption, and a backup that silently omitted a domain would be
  a far worse failure than one that includes it.

## MCP disposition

**Hidden domains: Included.** They needed no new tool and no new grant. Because remote domain listing and `domainId` selection both resolve the per-caller catalogue, a hidden domain is absent from `list_domains` and `query_domains` and fails selection closed for a credential without the `backstage` grant, and is present for one holding it. The deployment gate overrides the grant, as it does for records. Tests cover all three cases.

**Linking and moving: Deferred**, because the browser workflow and its preview do not exist yet, and a destructive cross-domain operation must not reach the remote surface before the reviewed browser flow settles. Linked item: this document. Owner: Agent. Review: 2026-10-01.

## What implementation changed about this design

Hiding was designed as "`IDomainCatalog.Snapshot` is filtered by backstage visibility". That could
not be done directly: the catalogue was a singleton and backstage authority is per-caller, so a
singleton cannot answer "may *you* see this". The split above — a singleton `IDomainRegistry`
holding every domain, and a per-caller scoped `IDomainCatalog` that filters — is what makes the
rule apply by default rather than at each surface.

Two consequences were not obvious beforehand:

- **Background sweeps needed their own selection.** Preview and media cleanup run in scopes with no
  account and no grant, so the caller-facing check would refuse a hidden domain and the sweep would
  fail every five minutes forever. `ICurrentDomainScope.UseForMaintenance` exists for exactly that
  and never appears on a request path.
- **Creating and renaming moved to the registry.** They are deployment administration and do not
  vary by caller; only concealment is an authority question, so only `SetHiddenAsync` sits on the
  per-caller view.
